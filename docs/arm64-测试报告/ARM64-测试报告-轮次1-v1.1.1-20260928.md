## 3. Findings（按重要度）

### F1 —— selftest 路径 MP3 转码 100% 失败（应用层 bug，可复现）

4/4 复现（14:53、14:58、15:12、15:26），错误：

```
[ERROR] MediaFoundation 转 MP3 失败，保留 WAV 文件 :: FileLoadException:
        The process cannot access the file because it is being used by another process. (0x80070020)
   at NAudio.MediaFoundation.MediaFoundationInterop.MFCreateSinkWriterFromURL(...)
   at NAudio.Wave.MediaFoundationEncoder.EncodeToMp3(...)
   at MusicRecorder.Core.AudioRecorder.WavFallbackSink.Complete()
```

**根因已定位（不是系统缺编码器，是自己锁自己的输出文件）：**

| 证据 | 结果 |
|---|---|
| Restart Manager（采集第 5 秒）对 `selftest.mp3` | 占用者 = `pid MusicRecorder`（本进程自己） |
| `FileShare.None` 探针 + 400ms 轮询时间线（selftest） | 采集开始 1.3s 后 `openable=False`，**一直锁到进程退出** → 结束时转码必然失败；最终 `selftest.mp3 = 0 B`、`selftest.wav = 1614662 B` |
| 同一探针（e2e 路径） | **全程 `openable=True`**（句柄可共享），转码成功 |
| 归档 | 4 次运行日志 ERROR 全部为 0x80070020，堆栈一致 |

即：**selftest 在采集开始时以独占方式（FileShare.None）创建/占用目标 .mp3 且到进程退出才释放；NAudio 的 MF sink writer 打不开同一路径 → 转码失败退化为 .wav。e2e 路径句柄可共享，故成功。**
失败发生在"编码器协商"之前，所以**这条错误具有误导性**：它不能用来判定"系统没有 MP3 编码器"。

### F2 —— 文档判读规则"产出 .wav = 系统无 MF MP3 编码器"在本机不成立

本机编码能力实测：

- e2e 两次成功产出可被系统解析的有效 MP3（96 kbps、44s、带 ID3）
- 注册表存在 `MP3 ACM Wrapper MFT`（`mfcore.dll`）、`MP3 Byte Stream Handler`、MP3 解码 MFT（`mp3dmod.dll`）
- 反向旁证：ACM 层 `acmFormatSuggest(PCM→0x0055)` 返回 `ACMERR_NOTPOSSIBLE(512)`（对照 PCM→PCM 返回 0），说明系统走的是 **MF 专用 MFT 而非 ACM 传统链路** —— 该探针不能用于否定 MF 能力

**结论：WOA 本机 MF→MP3 可用；selftest 的 .wav 是 F1 的文件锁造成的，不是缺编码器。**
→ 文档 §5 那条判读规则需要修正，否则每个测试者都会得出错误结论。

### F3 —— LAME 缺失的异常类型与文档不符

- 实际：`LAME 编码器不可用（FileLoadException: ），改用 MediaFoundation`
- 文档预期：`BadImageFormatException`
- 原因：ARM64 包内**根本没有** `libmp3lame*.dll`（解包目录只有 exe + 文档），是"文件不存在"而非"架构不匹配"
- 影响：判读表里"BadImageFormatException = 预期"的措辞应改为"文件缺失类异常（FileLoadException/NotFoundException）"

### F4 —— e2e 导出落在临时目录

`已保存：test-tone.mp3` 实际写到 `%TEMP%\MusicRecorder\e2e\`，GUI 导出目录 `C:\Users\Natsume\Music\MusicRecorder` **为空**。
若 e2e 定位为自测命令则正常，需开发者确认；否则是导出路径未走用户设置。

### F5 —— 倒回兜底逻辑在真机生效（正向发现）

`SMTC 定位到开头：True` 但进度未变化 → 自动改用「上一曲」让歌曲回到 0:00 → 录制正常。真机 WOA 下该兜底路径工作正常。

### F6 —— 文档缺口（沿用自上下文文档）

## 5. 建议（给开发）

1. **修 F1（优先级最高）**：`selftest` 不要在采集期间独占持有目标 .mp3（或转码前 `Close/Dispose` 句柄、改用临时 wav 中转）。可用本报告 §3 的 `FileShare.None` 探针做回归。
2. 修正判读文档：`.wav` 产出**不能**直接判定为"系统缺 MF MP3 编码器"；应先看 0x80070020（文件占用）还是 MF 类型不支持错误。
3. LAME 异常措辞改为 FileLoadException（包内无 dll）；LAME arm64 交叉编译仍是正式版建议项（速度、码率可控），但"必须"的前提需按 F2 重新评估。
4. 确认 e2e 导出目录语义（F4）。
5. 发布前更新 `使用说明.txt` 系统要求加入 ARM64（F6）。
6. 由具备 x64 模拟播放器的环境补测 Q5。
